二、验收判定与独立评测

W01【P0｜已实测、代码确认】缺少独立单帧时延证据，也可能显示“全部通过”
代码依据：tracking_system/backend/evaluation.py:381、388、392、442。
当前行为：有合格的 forward latency 独立证据时，时延指标采用 T=1 输入前向耗时的 P95；证据文件不存在时，却回退到批量报告的 measured_frame_ms 或 estimated_frame_ms。formal_evidence_complete 只检查关联率与基线改善率证据，没有检查时延证据是否被接受。
验证：临时构造关联率、改善率证据均被接受而没有独立时延文件的任务，能够得到 overall_status=passed、formal_evidence_complete=true，同时 latency evidence accepted=false。未修改历史证据。
影响：批量吞吐折算可替代独立单帧测试参与正式通过判定，证据完整性与页面结论不一致。
建议：正式判定必须要求独立 T=1 时延证据被接受；折算耗时保留为参考。现有但无效的时延证据已经会阻止回退，缺失证据也应按正式证据未齐处理。

W02【P0｜已实测、代码确认】手填基线优先于独立证据，却保留“正式证据齐备”
代码依据：tracking_system/backend/evaluation.py:400、408、442。
当前行为：baseline_rmse_m 手工参数优先参与改善率计算；即使已有合格的独立基线证据，也会被手填值覆盖。但 formal_evidence_complete 仍沿用原独立证据的 accepted 状态。
验证：临时夹具中，模型 RMSE=7 m、正式基线 RMSE=8 m 时改善率为 12.5%，该项不通过；传入手填基线 10 m 后改善率变为 30%，可以显示全部通过且正式证据齐备。
影响：复核值与正式验收值混用，可能改变验收结论。
建议：正式结论只使用绑定任务的独立证据；手填值作为明确标识的复核结果，不能继承正式证据状态。至少应拒绝手填覆盖，或将正式状态降为证据未齐。

W03【P0｜已实测、代码确认】V8 基线与模型输入时间轴不一致
代码依据：scripts/evaluation/test_rmse_improvement.py:283、291、294。
当前行为：IMM-JPDA 基线直接读取原始 MAT 的前 min(sequence_length, 原始帧数) 帧，滤波器 dt 固定为 0.1 s。
数据检查：track_data_highfi_0000.mat 的 GlobalTime 开头为 0、0.025、0.05、0.075、0.1 s，共 400 帧；其前 100 帧覆盖 0～2.475 s。供当前模型使用的兼容 PKL 为 100 帧、间隔 0.1 s，覆盖 0～9.9 s。
影响：同样写“100 帧、排除前 5 帧”，基线和模型实际评估的是不同时间范围；基线滤波步长也不匹配原始采样周期。任务签名一致不能消除这种差异。
建议：基线与模型对齐相同物理时间网格、目标集合、有效点与 warmup 范围，并采用匹配的 dt；对齐前不把 V8 改善率作为已完成公平比较的证据。

W04【P0｜已实测、代码确认】关联率证据与模型输入可能来自不同预处理链
代码依据：scripts/evaluation/test_association_accuracy.py:106 及其后关联统计、缺失统计重算逻辑；tracking_system/backend/evaluation.py:190。
当前行为：关联率脚本寻找对应原始 MAT，优先读取已有 AssociationStats；统计缺失时，在临时目录通过当前处理代码重新关联与注册，不覆盖历史 PKL。
已有发现：历史 PKL 缺少 AssociationStats；当前源码重注册得到的雷达、EO、ESM、快链路数组与历史 PKL 存在差异。
影响：模型可能在历史 PKL 上测 RMSE，关联率却来自当前源码重跑的处理结果。两者即使绑定同一任务、同名 MAT，也不能直接说明属于完全相同的一次数据处理链。
建议：冻结原始 MAT、处理代码、参数、处理结果和 AssociationStats；让模型与关联率使用同一批注册产物。若重建整条流程，应重新跑模型指标并生成对应的新证据。

W05【P0｜代码确认，公平性待统一】IMM-JPDA 与模型的比较条件未充分对齐
代码依据：scripts/evaluation/test_rmse_improvement.py:233、276、294、389；tracking_system/backend/evaluation.py:408。
当前基线：主要使用长机原始雷达和僚机原始快链路；不等同于模型使用的多平台雷达、EO、ESM 与注册后链路组合；以首帧真值状态初始化，固定 dt=0.1 s。模型还具有完整序列上下文。
影响：当前改善率混合了观测信息、初始化、时间上下文、预处理链和算法本身的差异。不能仅凭证据文件 valid_for_assessment=true 就认为这些条件已经对齐，也不能简单认定某一方一定占优。
建议：先定义正式比较条件，明确允许的传感器、链路、时间信息、初始化、有效点及 warmup；必要时补充匹配输入的基线或消融实验。报告中保留当前差异说明。

W06【P1｜代码确认，要求边界待统一】代码使用 RMSE≤8 m，需要与最终验收文字统一
代码依据：tracking_system/backend/evaluation.py:22 及 _criterion 的比较逻辑。
当前门限：位置 RMSE≤8 m、关联准确率≥85%、RMSE 改善率≥15%、推理耗时≤100 ms。
影响：如果最终协议要求严格“小于 8 m”，恰好等于 8 m 时当前代码仍会判通过。warmup、三维距离、总体聚合范围、时延统计方式也必须随门限一并明确。
建议：以最终确认的协议和验收细则统一比较符号与统计口径。本条只指出实现边界，不直接作合同合规结论。

三、模型管理与运行状态

W07【P1｜已实测、代码确认】更新磁盘权重后，刷新或重复激活不会自动加载新权重
代码依据：tracking_system/backend/model_manager.py:102、209、219、224。
当前行为：相同 model_id 和 device 已激活时返回 changed=false；刷新模型目录也不重新创建当前引擎。推理继续使用内存中的权重与缓存。
验证：已验证相同模型重复激活跳过加载、刷新前后引擎对象保持不变。
影响：覆盖同一路径的 best_model.pt 后，页面信息与实际内存模型可能不同步，容易把旧模型结果理解为新模型结果。
建议：模型使用不可变版本与权重哈希；提供显式重载，并在状态中展示当前内存权重身份。评测时冻结所用权重，而不只记录路径。

W08【P1｜代码确认，浏览器操作待验】当前激活模型无法在界面中直接切换设备

当前行为：部署按钮在 model.active 时禁用，但后端实际上支持同一模型切换到不同 device。
影响：无法直接把当前模型从 CPU 切换到 CUDA，或从 CUDA 切换回 CPU；需先切到其他模型再切回，操作路径不完整。
建议：区分“已激活同一模型、同一设备”和“同一模型需要切换设备”，允许后者提交；实际 CUDA 路径还需在具备设备的环境中验证。

W09【P1｜代码确认】模型卡片展示历史指标，容易被当成当前测试结论
代码依据：tracking_system/backend/model_manager.py:23、113。
当前行为：卡片读取指定历史运行的 metrics_summary.json，优先采用 metrics_wo_warmup；名称、运行记录和部分训练信息来自固定目录映射，不是对当前选择的数据重新评测。
已核对的历史去 warmup RMSE：V5 约 10.8061 m，V6 约 8.2141 m，V7 约 7.4882 m；V7 全帧 RMSE 约 7.6030 m。这些数值对应各自历史记录，不能自动视为当前 Web 任务的结果。
影响：历史指标与当前权重、数据、代码或任务范围未明确绑定时，可能造成达标与模型优劣误读；卡片时延也不应当作独立 T=1 证据。
建议：标注“历史评测”，同时显示运行 ID、数据/权重身份、warmup 和统计口径；当前任务结果单独展示。

六、耗时统计与运行身份

W16【P1｜已实测、代码确认】“单帧耗时”混用了多种不同指标
代码依据：tracking_system/backend/runtime.py:265；tracking_system/backend/batch_testing.py:610、645；tracking_system/backend/evaluation.py:381；tracking_system/frontend/src/views/PerformanceEvaluationView.vue:205。
当前至少存在四种口径：
1. 回放 per_frame_inference_ms：一次完整序列前向耗时除以该轨迹有效真值帧数。
2. 批量 measured_frame_ms：取首条轨迹，3 次预热、10 次 T=100 前向计时，序列平均耗时除以 100；P95 同样是序列耗时 P95 除以 100。
3. 批量 estimated_frame_ms：批量累计推理耗时除以评测有效点数。
4. 独立 forward latency：T=1 输入多次前向的 P95，证据合格时才是正式判定所用值。
问题：性能页“单帧实测”仍显示批量折算值，而验收指标可能使用独立 T=1 P95；其他页面又可能显示 estimated_frame_ms。
影响：整段吞吐折算、单次前向延迟和真实在线系统延迟不能互相替代。当前计时也不覆盖原始数据读取、关联注册、网络传输和前端显示的全链路耗时。
建议：统一命名并显示 T、batch、设备、预热次数、测量次数与统计量；正式门限旁显示实际参与判定的同一时延值。T=1 测速本身不证明 T=100 模型已经满足在线因果跟踪。

W17【P1｜代码确认】冷启动剔除与有效点分母的说明不充分
代码依据：tracking_system/backend/batch_testing.py:605、608、645、655。
当前行为：存在多个 batch 时，batch 耗时均值/P95 排除第一个 batch；total_inference_ms 仍包含它，estimated_frame_ms 和部分吞吐估计也由累计耗时计算。cold_start_batch_excluded 字段没有逐项限定适用指标。
另一个口径：有效点分母排除了 warmup 或无效真值点，但模型仍处理完整 T=100 输入。因此即使计算工作量相同，改变 warmup 也会改变 estimated_frame_ms。
影响：只读“已剔除冷启动”或“每帧耗时”可能误解实际计算方式。
建议：逐项标注冷启动处理；分别报告实际处理帧数、评分点数、总耗时、稳态前向时延和有效评分点吞吐。

W18【P1｜代码确认】运行签名与哈希覆盖不足，排队时也未冻结输入
代码依据：tracking_system/backend/batch_testing.py:34、458、515；tracking_system/backend/evaluation.py:78、190。
当前行为：runtime_code_sha256 只覆盖 src/model.py、src/dataset.py、src/dataset_pkl.py、backend/batch_testing.py；没有覆盖全部推理、场景选择、评估、预处理脚本、依赖版本和运行环境。权重与数据身份在任务实际执行时产生，不是在提交排队时冻结。
影响：排队后替换磁盘文件，任务会用执行时的内容；PKL 哈希也不能说明对应的原始 MAT 和生成代码。证据匹配任务中的已记录签名，不等于自动重新验证当前磁盘上的所有文件或比较条件。
建议：明确“提交配置”和“执行快照”的区别；冻结实际权重、文件列表、数据、完整依赖代码与环境；记录原始数据到注册产物的对应身份。

九、需要写入使用说明的系统边界

B01【代码确认】“实时回放”不是已经实现在线因果跟踪。
依据：tracking_system/backend/server.py:406、416、477；runtime.py:224。
Web 先对完整轨迹推理，再通过 WebSocket 逐帧发送缓存结果，默认每帧 sleep(0.05)。展示速度不等于数据时间步长，也不等于在线端到端延迟。若最终只要求完整序列推理与可视化，这是能力边界说明；若要求在线跟踪，则还需单独改造与验收。

B02【代码确认】Web 主推理和主批量路径消费预注册 PKL。
原始 MAT 的目标关联与注册不在 Web 主模型推理闭环中；独立证据脚本读取 MAT 不等于 Web 已支持实时原始传感器接入。交付流程要说明先处理数据、再推理的前置步骤。

B03【代码确认】模型管理是固定目录映射，不是通用模型仓库。
依据：tracking_system/backend/model_manager.py:23、74、102。
当前登记 V5/V6/V7 三个固定路径；刷新不会自动发现任意新训练目录，界面没有模型上传/注册功能，TRACKER_MODEL_PATH 也需匹配登记模型。激活选择保存在内存，重启后按配置重新默认选择，而非持久化沿用上次选择。

B04【已实测、代码确认】切模型不会自动切换默认数据目录。
同一个 ModelManager 的 data_dir 在初始化时确定，默认指向 V7 数据；切到 V5/V6 权重，单场景仍可使用该默认数据。这可以是有意的跨数据集测试，但页面和报告必须明确模型与数据身份。

B05【已实测、代码确认】“加载成功”与“已完成推理/达标”不同。
依据：tracking_system/backend/runtime.py:114；server.py:134；model_manager.py:209。
加载使用严格 state_dict 匹配并进入 eval 模式；没有自动执行代表样本前向。已实际在 CPU 加载 V5/V6/V7，当前架构均为 496,623 参数；加载失败时旧引擎会保留，这是已验证的保护行为。/api/health 首次访问也会触发初始化与模型加载，不能视为完全独立于模型和数据的存活探针。

B06【代码确认】批量任务串行，不等于全系统资源互斥。
依据：tracking_system/backend/batch_testing.py:223、298、610。
批量执行器 max_workers=1，批量任务之间串行；Web 推理等其他路径仍可能并发占用 CPU/GPU。num_workers 是 DataLoader 参数，不是批量任务并发数。取消通常在 batch 边界检查，末尾基准测试不保证即时取消；服务重启会将未结束任务标为 failed，不会自动续跑。

B07【代码确认】界面默认与直接 API 默认范围不同。
依据：tracking_system/frontend/src/views/BatchTestingView.vue:28；tracking_system/backend/server.py:123。
界面默认 V7 模型、scenario_cooperative、抽样 10 个场景、warmup=5、batch_size=64、workers=0；直接 API 默认数据集为 V7，max_scenarios=None。应在提交后和报告中明确实际范围，避免把快速检查当成完整验证。

B08【代码确认】批量中的 batch 与轨迹单位不是场景数或帧数。
依据：tracking_system/backend/batch_testing.py:180。
一个文件的多个 RegisteredTrack 会被拆成独立目标序列。batch_size=64 表示最多 64 条目标序列，不是 64 帧或 64 个场景；当前模型这一路径也不等价于对完整场景进行多目标身份连续性评测。

B09【已实测、代码确认】位置指标是有效真值点上的三维距离聚合。
依据：tracking_system/backend/batch_testing.py:115、558、629。
使用绝对 ECEF 位置的 x/y/z 三维欧氏距离；stable_stage_mask 排除每条序列前 warmup 个索引位置，而不是前 warmup 个有效观测。传感器缺测但真值有效的点仍参与评分，这是评估缺测跟踪能力的一种合理选择，需明确说明。
全局 RMSE=sqrt(全部有效点误差平方的均值)；mean_track_rmse_m 是各轨迹 RMSE 的简单均值，二者不同。位置点 P95 与轨迹 RMSE 的 P95 也不同。整体 RMSE 达标不能推导每条轨迹或每类场景全部达标。

B10【代码确认】独立单帧时延脚本覆盖范围有限。
依据：scripts/evaluation/benchmark_v7_acceptance.py:66。
当前脚本只接受 model_id=v7 且 dataset_id=v7，默认预热 50 次、测量 300 次，分别报告 T=1 与 T=100；同源场景别名也不会自动被接受。若其他模型/数据组合要形成同等级正式证据，需要扩展并重新验证。

B11【代码确认】后端功能验收通过不等于四项技术指标全部达标。
依据：tracking_system/backend/acceptance.py:81 及后续检查。
当前黑盒功能检查覆盖健康状态、模型激活、WebSocket、批量任务与下载等；对评估结果主要检查有四项指标且存在评测轨迹，没有以 overall_status=passed 作为整个功能检查的通过条件。
建议在交付记录中分别出具功能可用性结果与技术指标验收结果。
